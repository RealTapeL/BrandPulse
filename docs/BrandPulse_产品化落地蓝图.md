# BrandPulse 产品化落地蓝图

更新时间：2026-08-14

本文是架构图和业务逻辑图的文字基线。图中所有功能分为三类：

- **当前可用**：代码已经具备，且可以通过真实数据或真实 API 验证。
- **依赖条件**：代码已有入口，但必须补齐账号、授权、内部数据或运行环境。
- **规划功能**：尚未形成可承诺的生产能力，不能在页面、报告或汇报中伪装成已完成。

## 一、产品定位与事实边界

BrandPulse 是“商业项目品牌情报与运营分析平台”，不是单纯的爬虫、看板或聊天机器人。产品需要把下面四件事连成闭环：

1. 把项目、品牌、门店、品类和监测范围定义清楚。
2. 按监测范围获取真实数据，记录批次、来源、时间和失败原因。
3. 对数据做标准化、匹配、质量扫描，再计算可解释的确定性指标。
4. 通过看板、告警、报告、Agent 和预测模型，输出带口径和证据的业务结果。

必须坚持以下事实边界：

- 大众点评、小红书和地图数据只能说明公开口碑、公开声量、门店分布和竞争线索，不能替代 POS 销售、合同、客流或会员数据。
- 公开数据可以作为研究数据或 benchmark，但不能直接用于内部经营决策或标记为生产预测模型。
- Agent-Reach 只负责公开网页研究；外部研究的 URL、标题、发布时间和引用要与 BrandPulse 核心指标分层保存。
- 任何指标、报告、告警和预测都必须能回答：数据来自哪里、截至哪一天、使用了什么口径、质量是否通过。

## 二、当前代码基线

当前系统属于“模块化单体 + 异步任务”的形态：

| 层 | 当前实现 | 产品化要求 |
| --- | --- | --- |
| 前端 | Vue 3、Element Plus、ECharts、Pinia | 保持 API 驱动；页面展示范围、日期、来源和质量状态 |
| API | FastAPI，统一 `/api/v1`，本地会话 / 密码模式，请求级操作审计 | 增加组织、角色、项目权限、限流和幂等键 |
| 任务 | Redis + RQ，采集、Agent、ML、报告分队列 | 增加超时、取消、死信、队列监控、幂等键和资源隔离 |
| 采集 | WebBridge 大众点评 / 小红书，高德 API | 统一连接器契约、来源级质量、限流、重试和快照保存 |
| 数据库 | PostgreSQL，主数据、原始数据、指标、任务、治理、报告和 ML 台账；custom-format 备份与校验 | 增加完整恢复演练、敏感字段策略、异机备份和归档 |
| 原始文件 | 开发环境 `data/raw`、`data/processed` | 生产迁移到对象存储，保留 checksum、批次和生命周期 |
| 指标 | 确定性口碑、热度、SOV、趋势和自定义公式 | 建立指标契约、版本、质量门禁和回算机制 |
| Agent | Qwen 兼容接口、只读 SQL、受控工具、后台任务；API 操作进入审计台账 | 增加项目权限边界、工具超时、引用和敏感字段脱敏 |
| ML | 真实文件上传、训练、回测、导出、日志 | 增加模型注册、审批、上线、回滚、漂移监控和内部数据资格门禁 |

关键代码落点：采集任务在 `brandpulse.collectors.jobs` 和 `brandpulse.collectors.worker`，自动计划在 `brandpulse.monitoring.scheduler`，报告在 `brandpulse.reporting`，告警在 `brandpulse.alerts`，数据治理在 `brandpulse.data_governance`，Agent 在 `brandpulse.agent`，ML 在 `brandpulse.ml_forecasting`。后续实现应沿用这些边界，不要把业务逻辑重新塞回 API 路由或前端页面。

## 三、必须遵守的核心状态

### 1. 采集任务状态

`pending → running → completed`

异常路径：

- 失败且仍可重试：`running → retry_pending → running`
- 达到重试上限或无可验证记录：`running → failed`
- 来源级结果必须分别记录 `success`、`empty`、`failed`。
- 全部来源为空或失败时，任务不能标记为成功。
- 部分来源失败时，已采到的数据可以入库，但任务和计划必须显示 warning。

### 2. Agent 任务状态

`pending → running → success / failed`

Agent 不能直接绕过领域服务写业务表。查询走只读工具；采集、指标刷新、报告和训练等耗时动作必须进入对应 RQ 队列。任务表保存输入、上下文、RQ job、尝试次数、日志、输出和错误。

### 3. 报告状态

`pending → running → success / failed / skipped`

生成前必须通过数据新鲜度门禁。没有真实指标、来源为空、数据超过允许时效或质量不满足时，应记录 `skipped` 和原因，而不是生成一份看起来完整但事实过期的报告。

### 4. 内部数据导入状态

`uploaded → previewed → validated → approved → imported`

校验失败进入 `rejected` 或问题台账。没有完成品牌、门店和项目映射的记录不能写入经营事实表；人工确认不能被“自动猜测”替代。

### 5. 模型状态

`dataset_registered → validated → training → evaluated → approved → production`

公开基准数据的模型最多处于 `evaluated`，`production_eligible=false`。只有授权的内部数据、足够的历史长度、独立回测、误差阈值、负责人审批和上线记录齐备后，才能进入生产。

## 四、产品化分期

### P0：把当前真实链路运行稳定

目标：让“项目 / 品类监测”成为稳定产品能力。

- 连续运行自动采集计划，至少覆盖多个连续周期。
- 完成点评、小红书来源的登录态、空结果、验证码、失败和重试观测。
- 处理当前数据治理 warning，确认品牌别名和门店匹配关系。
- 配置 SMTP 或 Webhook，并验证触发、去重、失败重试和恢复通知。
- 启用至少一个日报或周报计划，验证报告新鲜度门禁、下载和历史追溯。
- 告警调度已收敛到独立的 `brandpulse.alerts.runner` 进程；FastAPI 只提供规则管理和手动检查入口，避免 API 多副本造成重复检查和重复通知。
- 统一记录 `trace_id`、`scope_id`、`crawl_job_id`、`source_name` 和 `captured_at`。

验收标准：连续运行期间没有重复入队、假成功、无来源报告和无法解释的指标变化；用户可以从一条报告记录追溯到采集任务和原始记录。

### P1：接入一类真实内部经营数据

目标：从“公开品牌情报”升级为“项目运营分析”。

- 先选 POS 销售或客流中的一类，不要同时接所有系统。
- 与业务负责人确定字段、单位、日期粒度、门店主键、权限和保留周期。
- 建立稳定连接器；Excel 作为过渡输入，不能作为长期人工复制流程。
- 完成品牌、门店、项目映射和人工确认页面。
- 计算同店销售、客单价、订单数、坪效或客流转化中的第一批指标。
- 公开指标和内部指标在页面、表、报告中分层展示。

验收标准：抽取一批业务人员可以核对的原始记录，与源系统总额、门店数和日期范围一致；任何内部指标都能回溯到原始经营记录。

### P2：生产预测与经营健康度

目标：让 ML 结果成为可管理、可回滚的产品资产。

- 建立数据集版本、特征版本、模型版本和预测批次。
- 训练前完成数据质量门禁、时间切分和独立回测。
- 展示 MAE、RMSE、WAPE、预测区间和基线对比，不只展示一个预测数字。
- 增加模型审批、上线、回滚、过期和漂移告警。
- 用内部销售、客流和合同数据构建租户健康度，不用死公式替代缺失事实。

验收标准：模型可以复现、比较、回滚；预测输出包含模型版本、训练数据范围、生成时间和适用范围。

### P3：多项目、多组织和知识库

目标：从单团队工具转为可交付产品。

- 增加组织、用户、角色、项目和数据权限。
- 敏感经营数据按字段或项目隔离，并有导出审批和审计日志。
- 引入文档、合同条款、制度、行业报告的知识库和向量检索。
- Qwen 模型按任务路由：主 Agent、复杂分析、批量摘要、Embedding。
- 引入对象存储、备份恢复、监控面板、部署流水线和发布回滚。

## 五、每个新功能的工程化准入清单

一个功能只有同时具备以下内容，才允许进入主分支并在产品页面出现：

1. 业务问题和用户角色明确。
2. 数据源、授权方式、更新频率和失败策略明确。
3. 数据表或接口契约确定，包含主键、时间、来源和质量字段。
4. 同步请求与异步任务边界确定，长任务可查询、可重试、可恢复。
5. 成功、空结果、失败、过期和权限不足都有明确状态。
6. 页面能展示加载中、空数据、错误、过期和不可用原因。
7. 日志能关联请求、任务、数据批次和用户操作。
8. 有真实数据验收样例，不以 mock 数据或硬编码数字验收。
9. 有 API 测试、关键流程测试和迁移脚本验证。
10. 有失败回滚和人工处理入口。

## 六、当前不应继续扩张的方向

- 在没有内部经营数据前，不继续包装销售预测、租户盈利或合同风险结论。
- 在没有通知凭据和连续运行记录前，不宣称自动告警已经生产可用。
- 在没有稳定来源适配器前，不一次性接入美团、抖音、微博、新闻等大量平台。
- 在没有权限、审计和敏感字段规则前，不开放 Agent 任意 SQL 或自动修改业务数据。
- 在没有模型注册和回测门禁前，不把公开数据模型标记为生产模型。

## 七、下一轮建议实施顺序

1. 先完成 P0 的连续运行、数据治理处理、通知和自动报告验收。
2. 再选一个真实内部数据源，完成数据契约、导入、映射和第一批经营指标。
3. 在内部数据形成稳定时间序列后，训练第一个内部预测模型并建立模型台账。
4. 最后补齐组织权限、部署、对象存储、完整恢复演练和知识库，进入多项目产品化。
