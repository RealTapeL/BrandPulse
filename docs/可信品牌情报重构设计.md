# BrandPulse 可信品牌情报重构设计

**状态：核心链路已实施（截至 2026-08-17）**
**目标：** 将现有“公开数据采集与展示”能力升级为一条可追溯的链路：

```text
监测范围 → 采集批次 → 原始观测与映射 → 质量校验 → 可发布快照
→ 指标与机会 → 告警/报告/助手 → 业务事项 → 人工反馈
```

本设计不将公开平台数据解释为销售、利润、租户健康度或确定的招商结论。大众点评、小红书和公开 POI 只用于公开口碑、公开内容、门店分布、竞品线索及候选品牌筛选；内部 POS、合同、客流等事实未接入时，系统必须明确显示“未接入，暂不能判断”。

## 1. 审计结论与当前风险

本次审计阅读了根目录 README、历史 PRD（该文件在当前工作区已删除，仅从当前 HEAD 读取）、产品化落地蓝图、全部数据库迁移、初始化 SQL、后端 API/采集/治理/指标/告警/报告/Agent/ML 模块以及 Vue 前端。

| 位置 | 问题类型 | 具体问题与影响 | 本次处理原则 |
| --- | --- | --- | --- |
| `monitoring_scopes.brand_id`、`crawl_jobs.brand_id` | 实体职责混淆 | 同一字段同时表示真实品牌和“城市×商场×品类”的采集数据集。例如实际库中同为“苏州·苏州中心·咖啡”出现 `LK001`、`KD001`、`MALL_906d5b65` 三个 scope。会让品牌页、采集、指标的归属语义不一致。 | 新模型以 `scope_id` 作为范围唯一事实；保留 `legacy_dataset_key` 兼容历史字段，绝不猜测其真实品牌归属。 |
| `dashboard.py`、`monitoring_repository.py` | 范围泄漏 | 现有范围查询仅使用 `brand_id + city + mall_name`；`category` 没有进入原始表和指标表过滤。将来同一商场的不同品类会混入。 | 所有新事实、快照、指标、报告、告警均由 `scope_id` 过滤；旧接口通过 scope 解析而非拼接不完整条件。 |
| `dp_shop_metrics`、`xhs_notes`、`brand_heat_daily` | 缺少事实归属 | 原始事实没有 `scope_id`、类别或映射状态；`raw_record_lineage` 仅覆盖部分较新的写入。小红书 `note_id` 还可能跨范围重复。 | 不修改或删除旧行；新增不可变的观测归属层，能由血缘可靠反查的才进入新范围事实，其他标记 `legacy_unclassified`。 |
| `indicators/*` | 口径/质量风险 | 口碑基准是全城混合池；SOV 仅按商场；热度把累计评价、累计点赞、门店数混为一个“热度”；动量未验证快照完整性和采集间隔。 | 将口径拆分为规模、近期活跃、质量、竞争、趋势；所有计算绑定快照、版本、比较池及降级策略。 |
| `reporting/service.py`、`reporting/runner.py` | 报告不可精确复现 | 以“最新日期”拼接点评、指标、小红书；生成的 `report_runs` 只保存日期而非可发布快照。 | 报告必须绑定 `snapshot_id`，只消费 `ready/published` 快照；不完整时跳过或经人工批准生成带水印版本。 |
| `data_governance/*` | 主数据生命周期不完整 | 当前可处理别名/问题，但人工匹配直接覆盖，没有生效期、证据、撤销或受影响快照回算记录。 | 新增映射决策与历史表，人工确认成为可撤销审计事件，而非覆盖式修改。 |
| `alerts/*` | 范围与业务闭环缺失 | 旧告警按 `brand_id` 读取旧聚合指标，可能跨品类混用；虽有去重、恢复和投递重试，但未固定触发时的快照证据。 | 新规则写入 `trusted_alert_rules`，绑定 `scope_id + metric_key`；每次检查将快照、指标质量和来源证据写入 `trusted_alert_evaluations`，并可创建事项。未绑定范围的历史规则保留但不由可信调度器执行。 |
| `custom_formulas` | 公式结果不可复现 | 旧公式按品牌/日期读取旧日表，既没有范围，也无法说明使用了哪个快照和哪些输入。 | 公式必须显式选择 `scope_id` 与 ready/published 快照；结果写入 `snapshot_formula_evaluations`，保存输入指标、公式定义、快照和失败原因。它不自动进入机会、报告或招商结论。 |
| `agent/*` | 证据/能力边界不足 | 已有 RBAC 和只读 SQL 拦截，但常规问答仍可由模型自由组合 SQL，回答结构不保证包含范围、快照和证据。 | 普通模式仅提供语义化只读工具；SQL 仅管理员高级调试使用；回复使用结构化证据包。 |

## 2. 目标实体关系

```text
Brand ─────< Store
  │           │
  │           └────< EntityMappingDecision >──── RawObservation
  │                                           └── SourceRun ─< CollectionRun
  │                                                               │
MonitoringScope ─< ScopeSourceRequirement                         │
       │          └───────────────< Snapshot >────────────────────┘
       │                                      │
       │                                      ├────< MetricObservation
       │                                      ├────< Opportunity
       │                                      ├────< ReportRun
       │                                      ├────< AlertEvaluation
       │                                      └────< FormulaEvaluation
       │                                                        │
       └──────────────────────────────< BusinessCase >─────────┘
```

### 核心实体的职责

| 实体 | 唯一职责 | 不承担的职责 |
| --- | --- | --- |
| `brands` / `Brand` | 已确认的真实品牌主数据。 | 采集数据集、商场范围、自动任务 ID。 |
| `stores` / `Store` | 已确认的真实物理门店及生命周期。 | 外部页面的未经确认门店名。 |
| `monitoring_scopes` / `MonitoringScope` | 城市 × 项目/商场 × 品类的业务范围。 | 真实品牌、某次采集批次。 |
| `collection_runs` | 一次完整采集编排，包含预期来源和触发上下文。 | 原始数据聚合、指标结论。 |
| `source_runs` | 一个 `collection_run` 中一个来源的结果、时间、错误和覆盖。 | 将失败来源按零值补齐。 |
| `raw_observations` | 原始记录与范围的可信关联、原始类别、标准类别及映射状态。 | 替代原始事实表。 |
| `data_snapshots` | 经来源覆盖和质量门禁确认、可被产品消费的数据发布单元。 | 任意一次成功的单来源爬取。 |
| `metric_observations` | 绑定快照、版本、比较池和证据的指标事实。 | 混合不同日期/来源的“最新值”。 |
| `trusted_alert_rules` / `trusted_alert_evaluations` | 范围绑定的告警规则及其触发时快照证据。 | 历史 `brand_id` 聚合范围、无证据的阈值结论。 |
| `snapshot_formula_evaluations` | 范围/快照绑定的自定义公式试验结果。 | 正式指标、机会评分或招商结论。 |

## 3. 新旧字段与兼容策略

| 旧对象 | 旧语义 | 新对象/字段 | 迁移策略 |
| --- | --- | --- | --- |
| `monitoring_scopes.brand_id` | 真实品牌或数据集键，语义不稳定 | `trusted_monitoring_scopes.legacy_dataset_key`；`scope_id` 是范围主键 | 旧表所有者与迁移账号不同，故不改写旧表结构；通过可信层和 `legacy_scope_links` 兼容关联。新代码不再把它称为/当作真实品牌。 |

| `dp_shop_metrics` / `xhs_notes` | 原始事实带模糊 `brand_id` | `raw_observations`（可信事实归属层） | 不破坏主键或历史数据；仅将存在可靠 `raw_record_lineage.scope_id` 的事实登记为可追溯观察。 |
| `brand_heat_daily` / `brand_indicators_daily` | 旧聚合与指标 | `metric_observations` | 保留旧表供历史页面/API；正式页面切到新指标事实。 |

旧 API、旧哈希路由和历史报表不删除。旧接口将继续返回旧格式，但会增加 `data_status`、`legacy` 或 `not_publishable` 说明，防止调用方把未映射历史行当作正式指标。

## 4. 快照状态机与来源状态

### 快照状态

```text
draft → collecting → partial → validating → ready → published
                   ↘ failed / rejected
published → superseded / expired
```

- `partial`：至少一个来源有已校验记录，但预期来源不完整；可浏览，不能默认用于正式跨来源指标、告警或报告。
- `ready`：满足该范围配置的来源与基本质量门禁，但不代表全部实体映射完成；未确认记录仍只可作为公开竞争线索。
- `published`：已显式发布的快照；新看板、范围告警和公式可读取 `ready/published`，但正式报告另有更严格的多来源与质量门禁。
- `rejected`：有原始数据但质量或映射不通过；保留证据与失败原因。

### 来源状态

| 状态 | 含义 |
| --- | --- |
| `success` | 已得到并完成基本校验的记录。 |
| `empty_validated` | 该来源明确无结果，且该“空”被规则认可。 |
| `failed` | 登录态、验证码、网络、解析或校验失败。 |
| `skipped` | 按范围配置未执行。 |
| `stale` | 结果超过范围定义的新鲜度。 |

`empty_validated` 不是 `success`。来源失败或未采集不得按 0 参与跨来源综合指标。

## 5. 指标定义与质量门禁

### 指标分类

1. **规模/存量：** 累计评价数、累计公开内容数、累计互动、门店覆盖。标记为累计，不使用“近期热度”措辞。
2. **近期活跃：** 可比发布快照间的新增评价、内容、互动、门店变动；仅在时间窗口和来源覆盖满足条件时输出。
3. **质量：** 贝叶斯加权口碑、小样本置信度、来源覆盖率、映射覆盖率、新鲜度。
4. **竞争：** 分别计算点评评价份额、小红书内容份额、小红书互动份额、门店数份额；每个份额记录分母、范围、窗口和来源。
5. **趋势：** 至少两个可比且完整度达标的快照；数据间隔、累计值下降、突增、映射变动不满足条件时输出“无结论”，不写零值。

### 口碑比较池与降级

门店口碑优先使用“同商场 × 同品类”，不足时依序退化为“同城市 × 同品类”→“同城市一级品类”；仍不足时不输出比较性结论。每条指标保存：`baseline_scope`、`baseline_level`、`sample_size`、`C`、`m`、`metric_version`、`calculated_at`、`source_snapshot_id`。

### 发布门禁

正式快照的基础门禁需同时满足：

- 预期来源结果均满足范围配置（或来源被明确配置为可选）；
- 已关联的原始观测可追溯至范围、来源运行和采集时间；
- 不存在阻断级质量问题；
- 品牌层指标仅消费已确认的品牌/门店映射；未确认记录不进入品牌指标；
- 指标版本和输入快照明确可复现。

### 告警与自定义公式边界

- 新告警仅可选 `data_freshness_hours`、`dp_review_count_stock`、`source_coverage_ratio`、`entity_mapping_coverage`。调度器只读取同一范围最新 `ready/published` 快照的 `valid` 指标；找不到值时记录“暂无可用指标值”，不回退旧热度或经营表。
- 每个告警历史会保留 `scope_id`、`snapshot_id`、指标质量和来源证据。历史未绑定规则显示为 `legacy_unscoped`，不自动执行。
- 自定义公式仅可使用选定快照内 `valid` 的 scope 级指标及用户显式参数。缺少变量时记录 `skipped` 与原因，不以 0 或默认值替代。其结果仅供分析试验，不能自动写入机会、报告、告警或 Agent 结论。

## 6. 机会、事项和报告状态机

### 候选品牌/机会

```text
discovered → master_confirmed → profile_incomplete → under_review
→ qualified → outreach → negotiation → introduced / rejected / archived
```

机会必须写入触发规则、指标窗口、快照、覆盖率、质量等级、置信度、影响范围、推荐动作和人工确认状态。它是需要验证的招商线索，不是招商结论或自动评分。

### 业务事项

```text
open → acknowledged → investigating → action_planned → in_progress → resolved → closed
```

事项可由告警、质量问题、采集失败、报告异常或机会创建；记录负责人、期限、评论、处理日志、外部链接、误报/有效性反馈、关闭人和关闭时间。规则确认率、误报率和处理时长基于这些真实结果计算。

### 报告

```text
queued → running → ready_for_review → approved → sent
                              ↘ failed / skipped
```

新报告绑定 `snapshot_id`、模板版本、指标版本、审核和分发记录；正式报告要求 fresh、多来源成功、质量 A/B 及可追溯指标。当前尚未实现“人工强制生成部分数据报告”，因此不完整或过期快照会直接 `skipped`，不会制造水印版正式文件。

## 7. API、权限与前端影响

### 新增 API 族

- `/api/v1/monitoring/scopes`：范围配置、来源要求、范围健康度。
- `/api/v1/snapshots`：列表、详情、来源覆盖、验证、发布。
- `/api/v1/data-mappings`：映射证据、确认、撤销、受影响快照。
- `/api/v1/metrics`：指标定义、版本、快照指标和证据。
- `/api/v1/opportunities`：机会发现、人工确认和生命周期。
- `/api/v1/cases`：事项、分派、评论、状态及反馈。
- `/api/v1/reports`：补充审核、分发、发送和下载记录。
- `/api/v1/alerts`：新增/更新规则携带 `scope_id`；历史规则保留 `legacy_unscoped` 状态。
- `/api/v1/formulas/{id}/run`：必须传入 `scope_id`，可选指定 `snapshot_id`；结果通过 `/values?scope_id=` 查询。
- `/api/v1/tables/raw_observations`、`/metric_observations`：必须传入 `scope_id`；旧 `brand_indicators_daily` 不再由新数据浏览器开放。

采集运行、报告运行、告警投递和 Agent 任务目前仍分别由其所属 API 读取；前端在“自动化中心”集中呈现。这是兼容期设计，尚未声明为单一 `/tasks` API。

原有 `/api/v1/dashboard`、`/api/v1/monitoring`、`/api/v1/reports`、`/api/v1/data-governance` 保持可用，在新链路稳定前继续提供兼容响应。

### 权限边界

现有 Admin / Operator / Viewer 不改变：

- `viewer` 仅查看范围、快照、指标、报告、事项和受控助手问答；
- `operator` 可配置范围/采集、处理映射和事项、创建/审核/分发报告、创建告警；
- `admin` 额外管理用户、权限、指标定义、全量审计和高级 SQL 调试。

普通助手只使用语义化工具，例如“读取当前已发布快照”“读取品牌事实证据”“读取开放事项”。只读 SQL 仅向管理员高级模式开放。具有副作用的采集、报告、告警、事项创建均由前端显式确认后调用 API，模型不得直接执行。

### 前端消费规则

既有五组导航（工作台、品牌洞察、数据中心、自动化中心、系统设置）保留。工作台、品牌洞察和机会雷达只读 `ready/published` 快照；单源数据会明确标注。正式报告在其之上增加完整多来源与质量门禁；`partial` 只能在数据中心/高级详情中显示，带来源缺失说明。机器学习保留在“系统设置 → 实验室”，没有通过内部数据资格门禁时不得显示生产可用标签。

## 8. 实施顺序、迁移与回滚

1. **Phase 1（已完成）：** `020_trusted_data_foundation.sql` 新增范围数据契约、采集/来源运行、快照和观测归属层；可靠历史血缘登记为可信记录，其余保留 `legacy_unclassified`。
2. **Phase 2（已完成）：** `021_snapshot_metric_semantics.sql` 与快照指标计算，旧“热度”不再作为正式结论来源。
3. **Phase 3（已完成）：** `022_master_data_operations.sql`：映射决策、别名历史、门店生命周期、显式 scope–store 映射和回算请求。
4. **Phase 4（已完成）：** 工作台、品牌详情、数据中心和机会雷达默认读取可信快照；无确认映射时明确空状态。
5. **Phase 5（已完成）：** `023`–`026`：机会信号、报告审核/投递重试、告警与数据质量可转业务事项。
6. **Phase 6（已完成核心边界）：** 普通助手改用语义化证据工具，管理员高级模式才保留只读 SQL；ML 保持实验室定位。组织级隔离和模型注册发布仍属后续部署能力。
7. **Phase 7（已完成）：** `027_trusted_alert_rules.sql`、`028_snapshot_formula_evaluations.sql`：告警与公式从旧 `brand_id`/日期聚合迁移为范围、快照、质量和证据绑定；数据中心不再公开旧热度/SOV 日表。

所有迁移只新增表、索引、兼容字段和可逆的数据登记，不删除历史行、不重写未确认的 `brand_id`。代码切换通过“新快照优先、旧视图降级”的适配层完成。若发现发布规则或历史关联有误，可将快照标记 `rejected/superseded` 并回退到旧兼容读路径；原始事实与迁移登记均保留。

## 9. 待产品负责人确认的配置

1. 每个品类正式报告的必需来源、可选来源和最长允许新鲜度。目前正式报告统一要求完整多来源成功；若业务接受单来源正式简报，需要明确审批和水印规则后再开放。
2. 项目/商场主数据的维护责任人，以及“我方项目”的判断来源。
3. 机会规则阈值、人工审批人及是否允许自动创建事项。
4. 报告模板、审核人、收件人、SMTP/Webhook 分发渠道。
5. 内部 POS、合同、客流和会员数据的授权范围、字段字典、刷新频率与脱敏要求。

## 10. 当前数据事实与未完成条件

- 当前已有一个“苏州 × 苏州中心 × 咖啡”可信范围；可追溯的公开点评历史观测已入可信层。
- 当前原始观测仍没有人工确认的品牌/门店映射，且小红书来源未形成成功结果。因此页面只显示“点评单源公开观测”和数据质量信号，不显示正式品牌结论、销售判断或自动招商结论。
- 系统已真实生成“实体映射未完成”“来源覆盖不完整”信号；它们可转为事项，但不会伪装成招商机会。
- SMTP/Webhook 报告分发实现为“生成 → 审核 → 用户显式发送 → 持久化重试”；不会在配置凭据后自动向任何收件人发信。
- 新建告警和品牌候选采集都必须选择已登记范围；候选品牌只写作待确认映射，不会因为采集参数而自动成为品牌事实。
- 旧热度/SOV 日表、无范围旧告警和旧 `custom_formula_values` 仅作历史兼容读，不再作为新页面、告警、公式或招商判断的数据源。
- 内部 POS、合同、客流、租约、面积等数据尚未接入；`store_operations` 为空时，销售趋势、坪效、经营预测均必须保持“未接入，暂不能判断”。
