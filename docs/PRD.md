# BrandPulse 品牌情报 Agent 系统 — 产品需求文档（PRD）

- 版本：v0.1（草稿，待确认）
- 日期：2026-07-22
- 依据文档：`BrandPulse_5-Agent系统架构.drawio`、`品牌分类体系.drawio`、`餐饮业态数据采集范围.drawio`
- 现状基线：阶段一已完成约 40%（三库基础设施、咖啡品牌高德采集、PG/Neo4j 仓储层、竞品关系图谱）

## 1. 需求

### 1.1 业务背景

面向商业地产商管运营场景。招商、运营团队在日常工作中需要大量品牌信息：某品牌口碑如何、在哪些城市拓店、是否适合引入本项目、现有租户经营是否健康。这些信息今天散落在 Excel、聊天记录、各个网站里，靠人肉查询，一次约 2 小时。

### 1.2 目标用户与痛点

| 用户 | 痛点 | 期望 |
|------|------|------|
| 招商同事 | 查一个品牌要翻多个网站和表格，信息碎片化 | 问一句，30 秒得到答案和引入建议 |
| 运营同事 | 租户出问题才知道，被动救火 | 系统比人更早发现异常，并提示该联系谁 |
| 管理层 | 招商决策缺数据依据 | 系统帮抓机会、提前退出风险租户 |

### 1.3 产品目标（三阶段，不可跳级）

1. **阶段一 · 品牌知识库与数据基础设施**：把零散品牌信息变成结构化、可查询的数据资产。
   完成标志：招商同事能查品牌、能看到数据、信息不再碎片化。
2. **阶段二 · 品牌监控与预警**：从"人找数据"变成"数据找人"。
   完成标志：系统自动发现品牌异常并分级推送给对应负责人。
3. **阶段三 · 智能分析与 Agent 化**：从"告诉你数据"到"告诉你结论、帮你行动"。
   完成标志：系统能对话、能推理、能建议、能生成外联内容。

### 1.4 范围

**纳入范围**
- 试点业态：餐饮 → 咖啡品类（瑞幸、库迪、星巴克）跑通后扩展茶饮、火锅
- 数据采集优先级：P0 内部营运数据（POS/合同/客流/招商记录）＞ P1 外部公开数据（高德、大众点评、官网/公众号）＞ P2 探索数据（外卖、短视频、投融资，暂缓）
- 三层存储：结构化实体表（PG）、关系网络（Neo4j）、非结构化 Chunk + 向量（Qdrant 嵌入模式）

**暂不纳入**
- 全品类一次性铺开（违反"先单品类跑通"原则）
- 外卖/抖音/付费报告等 P2 数据源
- 多租户 SaaS 化、权限体系（单团队内部使用）

### 1.5 衡量指标

- 阶段一：咖啡品类 3 个品牌档案完整可查；招商查单品牌信息 < 1 分钟
- 阶段二：预警准确率（命中/总预警）> 60%；日报推送无人工干预运行 2 周
- 阶段三：对话查询能正确回答事实性问题（基于知识库）；建议内容可追溯数据来源

## 2. 功能模块

按建设顺序排列，M1–M5 属阶段一，M6 属阶段二，M7 属阶段三。

### M1 品牌分类体系管理（部分完成）

- 六级业态分类树（零售/餐饮/儿童/休闲娱乐/生活服务/体验），层级统一 3–4 级：业态 → 品类 → 细分 → 品牌示例
- 七个补充标签维度：档次、品牌级别、经营方式、拓店状态、区域偏好、客群标签、主力店标签
- 现状：`category_dict` 表仅 3 条记录（咖啡/茶饮/烘焙），需按分类体系图补全并支持维护

### M2 数据采集（部分完成）

| 子模块 | 说明 | 状态 |
|--------|------|------|
| 高德地图采集 | POI 搜索 → 门店布局数据；品牌/城市/品类可配置 | ✅ 已实现（咖啡 3 品牌硬编码，需配置化） |
| Excel 批量导入 | 内部数据冷启动主通道：品牌档案、门店清单、POS 月报、合同台账按模板导入（已有 `data/sample/咖啡品牌情报面板_Excel模板.xlsx`） | ⬜ 未实现 |
| 手工录入 | 招商联系人、跟进记录等无法自动采集的数据，走面板表单 | ⬜ 未实现 |
| 大众点评采集 | 评分/评论数/人均消费 → 品牌热度指标 | ✅ 已实现（WebBridge 方案，商场+品类搜索可用） |
| 官网/公众号/新闻 | 品牌动态文本 → Chunk 知识库 | ⬜ 未实现（阶段一后期） |
| Mock 采集器 | 无 API Key 时生成示例数据验证流程 | ✅ 已实现 |

### M3 数据清洗与标准化

- 命名统一：同一品牌/商场的多种写法归一（别名表）
- 分类映射：外部数据分类口径对齐到 M1 分类树
- 去重补全：重复门店合并、缺失值处理
- 质量校验：异常值识别；`data_source_logs` 表记录每次采集的来源、数量、状态（数据血缘）

### M4 三层存储（大部分完成）

| 层 | 载体 | 内容 | 状态 |
|----|------|------|------|
| 实体层 | PostgreSQL | brands / companies / stores / brand_metrics / store_operations / brand_contacts / category_dict / data_source_logs | ✅ 表结构已建（malls 实体表待补，knowledge_chunks 已补） |
| 关系层 | Neo4j | Brand–Store–City–Mall 节点，HAS_STORE / LOCATED_IN / IN_MALL / COMPETES_WITH 关系 | ✅ 已实现 |
| Chunk 层 | Qdrant 嵌入模式（向量）+ PG knowledge_chunks（文本元数据） | 新闻/报告/评论等非结构化文本，供 RAG 检索 | ⬜ 仓储已通，chunk 切分与 embedding 流程未实现 |

### M5 查询与分析（阶段一交付核心）

- **品牌档案卡**：单品牌全景视图（基础信息 + 标签 + 门店分布 + 竞品 + 联系人）
- **筛选查询**：按业态/品类/城市/档次/拓店状态组合筛选
- **商场品牌布局分析**：对标商场品牌组合、业态占比、竞品同场分析（基于 Neo4j 图）
- **数据 API**：供阶段二监控和阶段三 Agent 调用的内部查询接口
- 载体：Streamlit 面板（快速验证），后续按需升级 Web

### M6 监控与预警（阶段二）

- 指标体系：热度（评分变化/讨论量）、拓店动态（新开/关店）、经营健康（租售比/坪效趋势）、风险（负面舆情/合同到期）
- 规则引擎：阈值规则 / 趋势规则 / 对比规则 / 事件规则 / 组合规则，规则可配置
- 定时采集：单机 APScheduler/cron（不上 Airflow，见 §3）
- 分级推送：高优先级立即推（企业微信/钉钉机器人 webhook），中低优先级日报/周报汇总

### M7 智能分析与 Agent（阶段三）—— 5-Agent 流水线

采用与 [BettaFish](https://github.com/666ghj/BettaFish) 一致的多 Agent 分工思路，将"分析一个品牌/商场问题"拆成 5 个独立 Agent 串行/并行协作，避免单一大模型幻觉和职责混乱。原 BettaFish 的"多模态分析 Agent"替换为更适合商业情报场景的"数据分析 Agent"。

| Agent | 职责 | 输入 | 输出 | 与数据层关系 |
|------|------|------|------|------------|
| **爬虫 Agent** | 批量采集社交媒体、新闻、官网、地图 POI 等外部数据 | 目标品牌/关键词/城市/周期 | 原始结构化或半结构化数据 → 写入 data/raw → 经清洗后进入实体层/Chunk 层 | 产出阶段一/二数据源 |
| **网页搜索 Agent** | 实时搜索品牌最新动态（融资、拓店、关店、高管变动） | 品牌名 + 查询意图（如"最近 30 天拓店新闻"） | 搜索结果摘要 + 来源链接 → 直接进入 Chunk 层或补充实体层 | 阶段三实时查新，不做批量沉淀 |
| **数据库挖掘 Agent** | 从 PG 结构化数据中查事实；把自然语言问题转 SQL/Cypher 返回精确数据 | 用户问题（如"瑞幸上海门店数""库迪和瑞幸同场率"） | 精确事实表/指标集合 | 消费实体层 + 关系层 |
| **数据分析 Agent** | 对数据库挖掘 Agent 的结果做统计、趋势、对比、异常检测、归因 | 事实数据 + 时间范围 + 分析目标 | 洞察结论（如"瑞幸近 3 个月拓店放缓，库迪仍激进"） | 消费实体层 + 指标表 |
| **报表综合 Agent** | 模板驱动的 IR（中间表示）生成 + 多格式渲染（PDF/HTML/Word） | 前四个 Agent 的输出 + 报告模板（品牌档案/竞品分析/招商简报/风险预警） | 可直接阅读/汇报的多格式报告 | 不直接读库，只消费上游 Agent 输出 |

**典型运行流程**

```
用户提问："瑞幸最近拓店情况如何，是否值得引入？"
         │
         ├─→ 网页搜索 Agent ──→ 最近新闻/融资动态
         │
         └─→ 数据库挖掘 Agent ──→ 全国门店数、城市分布、竞品同场率
                       │
                       ▼
              数据分析 Agent（趋势/对比/异常）
                       │
                       ▼
              报表综合 Agent（按招商简报模板）
                       │
                       ▼
              PDF/HTML 报告 + 数据来源引用
```

**关键边界**

- 数据库挖掘 Agent 只"查数"、数据分析 Agent 只"算数"，避免一个 Agent 既写 SQL 又下结论。
- 网页搜索 Agent 只用于"实时查新"，不做常规沉淀；常规沉淀由爬虫 Agent 按调度完成。
- 报表综合 Agent 必须先接收前四个 Agent 的输出，不能直接读取数据库，强制所有结论经过"数据层 → 挖掘 → 分析 → 报告"的链路，保证可追溯。
- 阶段三启动前，阶段一/二必须已提供完整数据 API 和 Chunk 知识库，否则 Agent 无米下锅。

### 3.2 本机环境约束（已确认的事实）

开发机为 **ARM aarch64 / 4 核 / 4GB 内存 / 内核 16KB 页 / 无 Docker**，对方案有以下决定性影响：

- **Qdrant**：官方二进制不兼容 16KB 页内核 → 已改为 **qdrant-client 嵌入模式**（`QDRANT_PATH=brandpulse-infra/data/qdrant-local`，API 与服务器模式一致，已验证读写检索通过）。限制：同一时刻只允许一个进程访问，面板与采集任务不能同时写向量库。
- **PostgreSQL**：走 Debian apt 原生安装（`apt install postgresql`），初始化时执行 `brandpulse-infra/init-scripts/01_create_tables.sql`。
- **Neo4j**：官方 tar 包 + ARM JDK 原生运行，JVM 堆压到 512m。4GB 内存同时跑 PG + Neo4j + Python 较紧张， Neo4j 不使用时建议停掉；阶段一后期若成为瓶颈，备选方案是把竞品关系退回 PG 的 `brand_relationships` 表（表已存在）。
- **LLM / Embedding**：本地不跑模型（内存不够），一律走 OpenAI 兼容 HTTP API（如 DeepSeek / 硅基流动，待定，见 §8）。
- **定时任务**：APScheduler 或系统 cron，不引入 Airflow/RabbitMQ 等重型组件。
- `brandpulse-infra/docker-compose.yml` 保留，供未来迁移到标准 x86 服务器时使用。

## 4. 目录结构（目标态）

保留现有 `modules/`（可复用逻辑）+ `stage/`（阶段脚本）约定，但把各领域模块从 `utils/` 下提出——`utils/` 只放 config/logger 这类真工具。迁移成本低（改 import），可读性收益大。

```
BrandPulse/
├── brandpulse-infra/              # 基础设施（compose 备用 + init SQL + 本地数据目录）
├── docs/                          # 设计文档、drawio、本 PRD
├── data/{raw,processed,sample}    # 原始数据 / 清洗后数据 / 模板样例
├── src/
│   ├── main.py                    # CLI 入口（argparse 子命令）
│   └── brandpulse/
│       ├── config/                # 配置（自 utils/config 迁入）
│       ├── logger/                # 日志（自 utils/logger 迁入）
│       ├── db_clients/            # PG/Neo4j/Qdrant 客户端（自 utils 迁入）
│       ├── collectors/            # M2：amap / dianping / excel_import / mock
│       ├── processing/            # M3：命名统一、去重、质量校验、血缘
│       ├── storage/               # M4：pg / neo4j / qdrant 仓储
│       ├── knowledge/             # M4/M7：chunk 切分、embedding、RAG 检索

│       ├── agent/                 # M7：5-Agent 流水线
│       │   ├── crawler_agent/     # 批量爬虫 Agent
│       │   ├── web_search_agent/  # 实时网页搜索 Agent
│       │   ├── data_mining_agent/ # 数据库挖掘 Agent（NL→SQL/Cypher）
│       │   ├── data_analysis_agent/ # 数据分析 Agent（统计/趋势/对比）
│       │   └── report_agent/      # 报表综合 Agent（IR + 多格式渲染）
│       └── panel/                 # M5：Streamlit 查询面板
```

## 5. 风险点

| # | 风险 | 影响 | 缓解措施 |
|---|------|------|----------|
| 1 | 大众点评/小红书爬虫违反平台条款、反爬封号 | 热度数据源中断 | 优先级降为 P1 后期；先靠高德+官网+内部数据；如需点评数据优先手工/半自动导出；控制频率、遵守 robots 与 ToS |
| 2 | 内部经营数据拿不到（无 POS/合同系统接口） | M2/M6 核心价值落空 | Excel 模板导入为兜底方案（领导汇报口径已确认该路径）；先造样例数据跑通全链路 |
| 3 | 4GB 内存同时跑 PG+Neo4j+Python+面板 | OOM、开发机卡顿 | Neo4j 堆限 512m、不用时停服；备选：竞品关系退回 PG 表；不引入重型中间件 |
| 4 | 嵌入模式 Qdrant 单进程文件锁 | 面板和采集同时写会失败 | 采集任务与面板分时段运行；写操作集中在 stage 脚本 |
| 5 | 数据质量差导致 GIGO（路线图自警示） | 分析结论不可信 | M3 清洗校验前置；每条数据记录来源与更新时间（血缘）；面板展示数据来源 |
| 6 | LLM 幻觉 | 阶段三结论误导决策 | RAG 强制引用出处；无数据支撑的问题明确回答"不知道" |
| 7 | 预警规则过敏感 → "狼来了" | 用户麻木弃用 | 规则默认保守阈值；分级推送；预留反馈调优机制 |
| 8 | 高德 API 配额限制（个人 key QPS/日限额） | 全国采集不完整 | 分页限速已实现；分城市分批次采集；原始响应留存 data/raw 避免重复请求 |
| 9 | 过早扩品类/上 Agent（路线图自警示） | 摊子铺大做不完 | 开发顺序强制：咖啡品类阶段一闭环 → 验收 → 才启动阶段二 |

## 6. 开发顺序（里程碑）

每个里程碑有明确交付物和验收标准，串行执行。
