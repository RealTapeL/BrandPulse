# BrandPulse 品牌情报分析系统 — 产品需求文档（PRD）

- 版本：v0.3
- 日期：2026-07-31
- 依据文档：`BrandPulse_系统架构.drawio`、`品牌分类体系.drawio`、`餐饮业态数据采集范围.drawio`、`品牌热度布局分布_数据表设计.drawio`
- 现状基线：外部数据链路（采集 → 入库 → 指标 → 看板）已跑通；Web 平台已接入真实后端；对话与 Agent 依赖已配置的 LLM 服务

## 1. 需求

### 1.1 业务背景

面向商业地产商管运营场景。招商、运营团队日常需要大量品牌信息：某品牌口碑如何、在哪些城市拓店、是否适合引入本项目、现有租户经营是否健康。这些信息散落在 Excel、聊天记录和各网站里，靠人肉查询，一次约 2 小时。

### 1.2 目标用户与痛点

| 用户 | 痛点 | 期望 |
|------|------|------|
| 招商同事 | 查一个品牌要翻多个网站和表格，信息碎片化 | 问一句，30 秒得到答案和引入建议 |
| 运营同事 | 租户出问题才知道，被动救火 | 系统比人更早发现异常，并提示该联系谁 |
| 管理层 | 招商决策缺数据依据 | 用数据支撑招商与调铺决策 |

### 1.3 产品目标（三阶段，不可跳级）

1. **阶段一 · 数据基础设施与可视化**：把零散品牌信息变成结构化、可查询、可视化的数据资产。
   完成标志：招商同事能在 Web 平台上查数据、看指标。
2. **阶段二 · 品牌监控与预警**：从「人找数据」变成「数据找人」。
   完成标志：系统自动发现品牌异常并分级推送给对应负责人。
3. **阶段三 · 智能分析与决策辅助**：从「告诉你数据」到「告诉你结论」。
   完成标志：对话问答、自动报告，且每条结论可追溯数据来源。

### 1.4 范围

**纳入范围**

- 试点业态：餐饮 → 咖啡品类，跑通后扩展茶饮、火锅
- 外部公开数据：大众点评（评分/评价数/人均）、小红书（笔记/点赞），通过 Kimi WebBridge 驱动真实浏览器采集
- 内部营运数据：POS / 合同 / 客流，以 Excel 模板导入为接入方式
- 存储：PostgreSQL 单一数据库

**暂不纳入**

- 全品类一次性铺开
- 外卖 / 短视频 / 付费报告等数据源
- 多租户 SaaS 化、权限体系（单团队内部使用）

### 1.5 衡量指标

- 阶段一：商场 × 品类采集 10 分钟内完成入库；看板数据与库内一致；招商查单商场品类信息 < 1 分钟
- 阶段二：预警准确率（命中/总预警）> 60%；日报推送无人工干预运行 2 周
- 阶段三：对话查询能正确回答事实性问题；结论均标注数据来源表

## 3. 技术方案

### 3.1 总体架构

```
外部数据源（大众点评 / 小红书 / 高德）
        │  Kimi WebBridge（驱动已登录的真实浏览器）
        ▼
采集层 collectors ──► PostgreSQL（原始表 + 聚合表）+ JSON 缓存
        │
        ▼
指标层 indicators（口碑 / 热度 / SOV / 趋势，确定性代码）
        │  写入 brand_indicators_daily
        ▼
机器学习层 ml.forecasting（公开数据适配 / 时间特征 / 回测 / 模型工件）
        │  训练运行写入 ml_training_runs，模型明确标注生产资格
        ▼
FastAPI（认证 / 看板 / 品牌 / 采集任务 / 数据表 / 公式 / Agent / 对话 / 预测接口）
        │
        ▼
Vue3 + Element Plus Web 平台（看板 / 对话 / 数据表 / 公式）

对话助手（Agent Harness）：
用户提问 → Pydantic AI 工具循环（LLM 只做调度）
        → 工具层 = 现有代码薄封装（query_db / run_indicators / crawl / list_tables）
        → PostgreSQL / 采集管道
```

设计约束：所有数字计算走确定性代码，LLM 只负责理解意图、选择工具、组织语言，保证指标可复现、结论可审计。

### 3.2 部署环境

- 开发机：x86_64 Arch Linux，本机直装，不使用 Docker
- 数据库：PostgreSQL 单库（`brandpulse`），初始化脚本见 `brandpulse-infra/init-scripts/`
- LLM / Embedding：本地不跑模型，一律走 OpenAI 兼容 HTTP API
- 采集通道：Kimi WebBridge MCP（`ws://127.0.0.1:10086`），依赖桌面浏览器扩展保持在线

### 3.3 技术选型

| 领域 | 选型 | 说明 |
|------|------|------|
| 语言 | Python 3.14 | `.venv` |
| 数据库 | PostgreSQL + SQLAlchemy | 唯一数据库 |
| 采集 | Kimi WebBridge + 配置化 crawler 引擎 | extractor 插件式扩展 |
| 后端 | FastAPI | 看板接口 + 前端静态托管 |
| 前端 | Vue3 + Element Plus + ECharts + vue-router | hash 路由 |
| Agent | Pydantic AI | 工具循环薄层，模型无关 |
| 测试 | pytest + Vitest | 后端 75 项、前端 10 项 |

### 3.4 分支模型

`develop` 为集成主线；功能开发从 `develop` 拉 `feature/xxx`，完成后合回；`main` 用于发布。链式功能分支（backend-frontend-split / indicators / dashboard-api / agent-harness / frontend-app）已全部并入 `develop`。

## 4. 风险点

| # | 风险 | 影响 | 缓解措施 |
|---|------|------|----------|
| 1 | 点评/小红书风控升级、账号封禁 | 热度数据源中断 | 控制频率；验证码人工兜底；原始响应留存 JSON 缓存避免重复采集 |
| 2 | 内部经营数据拿不到 | 监控预警核心价值落空 | Excel 模板导入为兜底；先用外部数据跑通指标与看板 |
| 3 | 数据质量差导致 GIGO | 分析结论不可信 | 清洗校验前置；每条数据记录来源与采集时间 |
| 4 | LLM 幻觉 | 结论误导决策 | 工具强制返回真实数据；系统提示词禁止编造数字；回答标注来源表 |
| 5 | LLM API 配额与成本 | 对话功能不可用 | 对话为辅助入口，看板与 CLI 不依赖 LLM |
| 6 | 预警规则过敏感 | 用户麻木弃用 | 默认保守阈值；分级推送；预留反馈调优机制 |
| 7 | 高德 API 配额限制 | 门店采集不完整 | 分页限速；分城市分批采集 |
